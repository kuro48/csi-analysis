# Phase 3 指示書 — folding による連続監視

親計画: `RESEARCH_ROADMAP.md`
前提: **Phase 1 完了**（硬化版証明書回路）。Phase 2 と並行着手可。
担当: ZKP エージェント（folding / arkworks 系に習熟が望ましい）

## 0. このフェーズのゴール（完了条件）

**まず feasibility 判断（Go/No-Go）まで**が最優先の完了条件。本実装はその後。

1. **Go/No-Go 判断**: 既存の（硬化版）証明書回路 1 個を Sonobe/Nova のステップ関数として
   折り畳めるかを 1〜2 週間で検証し、判断レポートを出す。
2. （Go の場合）スライディングウィンドウごとの呼吸解析を折り畳み、
   「全区間正常」または「異常ウィンドウ数 ≤ k」を**単一の短い証明**で示すプロトタイプ。
3. （No-Go の場合）フォールバック（ウィンドウ毎 Groth16 証明の Merkle 集約）の設計と最小実装。

## 1. 命題

一晩分の連続 CSI をスライディングウィンドウに分割し、各ウィンドウで Phase 1/2 の
証明書回路を評価。folding（IVC）でこれを累積し、アキュムレータに:

- 処理ウィンドウ数
- 異常ウィンドウ数（≒ 検証可能な AHI 相当の頻度推定）
- ウィンドウコミットメントのランニングハッシュ（連続性・改ざん耐性）

を持たせ、最終的に「異常ウィンドウ数 ≤ k」を単一証明で開示する。
**いつ異常だったかは明かさず頻度だけ証明**できる点がプライバシー上の主張。

## 2. 作業手順

### タスク 3-1: feasibility 実験（最優先・タイムボックス 1〜2 週）

- `research/phase3_folding/feasibility/`。
- Sonobe（Nova/HyperNova, Circom フロントエンド）で、Phase 1 の証明書回路
  （縮小版で可: T を小さく、テーブルを軽く）を 1 ステップ関数として登録し、
  数ステップ折り畳めるか、Solidity 検証器が生成できるかを確認。
- 固定小数点回路との相性、メモリ/RAM 要件、ビルドの通し方を記録。
- **判断レポート** `research/phase3_folding/GO_NO_GO.md` を出す:
  - Go 条件例: 縮小回路が 10 ステップ以上折り畳め、証明サイズがステップ数に依存せず一定、
    ビルドが再現可能。
  - No-Go なら理由（ツール成熟度・固定小数点非対応・RAM 等）を明記しフォールバックへ。

### タスク 3-2a（Go の場合）: folding プロトタイプ

- ステップ回路 = Phase 2 の committed 証明書回路 + ウィンドウ境界連鎖
  （前ウィンドウ末尾コミットメントとの整合）。
- アキュムレータ状態（ウィンドウ数・異常数・ランニングハッシュ）を IVC で更新。
- 最終証明で「異常ウィンドウ数 ≤ k」を公開検証。
- 評価: ステップ数に対する証明サイズ・検証時間の一定性、全体証明生成時間。

### タスク 3-2b（No-Go の場合）: Merkle 集約フォールバック

- 各ウィンドウで既存 Groth16 証明を生成 → 証明群はオフチェーン保持、
  publicSignals の Merkle ルートのみ `ZKProofRegistry` に記録。
- 「区間内の全証明が isNormal」を Merkle 包含で検証可能にする。
- 研究的新規性は folding 版より落ちるが、システムとしては成立。異常頻度の集計は
  ルート下の葉のカウントで対応。

### タスク 3-3: 応用評価

- 合成データ（正常呼吸に無呼吸区間・頻呼吸区間を挿入）で「異常ウィンドウ数 ≤ k」の
  検証可能推定が真の挿入頻度とどれだけ一致するかを評価。
- プライバシー主張（異常時刻の非開示）の説明を `research/phase3_folding/PRIVACY.md` に整理。

## 4. 制約・注意

- **feasibility を出すまで本実装に着手しない**。ツール成熟度リスクが高いフェーズ。
- 本番フロー・既存回路は不変。
- Sonobe/arkworks は Rust。Groth16/snarkjs スタックからの部分移行になる点を許容。
- 縮小回路での feasibility が本番サイズ回路の性能を保証しない点に注意（RAM でスケールしない
  可能性）。判断レポートに本番サイズ外挿の見積もりを含める。
